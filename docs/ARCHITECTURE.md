# Архитектура

## Текущая реализация

- Vite + React + TypeScript с `strict`-проверкой; интерфейс без тяжёлой UI-библиотеки.
- `src/domain/nutrition.ts`: профиль, валидация, BMR/TDEE, целевая энергия и округление.
- `src/domain/recipes.ts`: демонстрационные структурированные рецепты, пищевая ценность ингредиентов с явной базовой единицей (г/мл), фильтр ограничений и расчёт порции; несовпадающие объём/масса отвергаются.
- `src/domain/planning.ts`: детерминированная генерация, дневные итоги и замена блюда.
- `src/domain/shopping.ts`: сборка/объединение ингредиентов для плана.
- `src/domain/pricing.ts`: независимый детерминированный расчёт упаковок и стоимости в копейках; интерфейс пока не показывает цену без проверенного товарного каталога.
- `src/domain/storage.ts`: версия ключа локального хранилища и явные ошибки записи.
- `src/ui/`: пользовательский интерфейс, адаптивные стили и состояния.
- `src/domain/nutrition.test.ts`: проверки расчётов питания, планирования, покупок и упаковочной арифметики.

## Границы текущей версии

Внешний сервер/БД, авторизация, синхронизация, семейные участники, каталог товаров и цен, pantry editor, единицы штук/массы, администрирование и CSV-импорт не реализованы. Не заявляется интеграция магазина. Набор рецептов — только демонстрационные ручные значения без верифицированного источника.

## Дальнейшее развитие

Сохранять чистые доменные функции отдельно от React. Перед серверным хранением спроектировать нормализованную PostgreSQL схему (профили/домохозяйства/участники/цели/предпочтения/аллергии/продукты/цены/магазины/источники/рецепты/версии/ингредиенты/планы/дни/блюда/участники/списки/запасы/избранное/история цен/обратная связь), миграции, ограничения и аудит. Включить RLS и проверку членства сервером. Хранить деньги целыми копейками или `NUMERIC`, сохранять снимки рецепта/цены при необходимости и версионировать изменения.

Каталог ингредиентов и магазинных SKU/упаковок/цен должен быть раздельным. Для будущей интеграции сначала проверить официальные условия, право доступа, географию и возможность фактического использования; не строить фиктивный API-адаптер.
